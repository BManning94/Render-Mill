# LumenCraft v0.11.0 — Engineering report

Rendering quality, performance and stability overhaul of the v0.10.0 codebase.
Architecture is unchanged: native Rust, wgpu 22 + WGSL compute path tracer,
egui/eframe UI. No new runtime dependencies (one dev-dependency: `naga`, the
WGSL compiler wgpu already uses, for offline shader validation).

**Test environment for every number below:** cloud Linux VM, 2 CPU cores,
~6 GB memory limit, *no GPU* — wgpu runs on **llvmpipe/lavapipe** (Mesa's
CPU implementation of Vulkan), Open Image Denoise on the CPU. No RTX
hardware was available, so **no RTX 5080/5090 numbers are claimed**. Timings
are useful for *relative* comparisons of the two versions on the same device;
noise and memory figures are hardware-independent.

Commits (on top of `2996cb5` v0.10.0): Phase 1 `0e7b38f`, Phases 2–4
`d8beb37`, Phase 5 `74ce94f`, Phase 6 `037ca29`, formatting-only `49d4386`,
then the final tuning/benchmark/release commit.

## Phase 1 — BVH traversal and rendering correctness

| # | Verified problem (v0.10) | Root cause | Fix |
|---|---|---|---|
| 1.1 | Traversal could silently skip geometry | `if (sp < 46)` in `trace()` pushed **neither** child when ≥46 entries were on the 48-entry stack | Depth bounded by construction: SAH for ≤32 levels, then object-median splits (halve the triangle count per level) ⇒ depth ≤ 63 for any input up to 2³² triangles; stack sized to 64 (≥ max occupancy = depth + 1); `assert!` in the builder; capacity check removed |
| 1.2 | Small details missing | Triangles with `|cross|² < 1e-14` (area < ~5·10⁻⁸ m²) dropped; `|det| < 1e-12` rejected small triangles in the intersector | Only exactly-degenerate triangles are skipped (`det == 0`, `area² ≤ 0`). Measured: +12 triangles kept in the demo, +516 in the large exterior |
| 1.3 | One bad vertex could hide unrelated geometry | NaN/∞ vertex ⇒ NaN node bounds ⇒ `ray_box` fails for that whole subtree | Non-finite triangles (and NaN normals/UVs) filtered before the build; count logged |
| 1.4 | Hairline cracks / light leaks at shared edges | Strict Möller–Trumbore edge tests | Slightly inclusive tests (±1e-6) |
| 1.5 | Self-shadowing speckle far from the origin | Fixed 1 mm ray offset < float spacing at survey coordinates | `offset_ray`: offset scales with coordinate magnitude (2e-4 + 1e-5·max|p|) |
| 1.6 | Sun counted twice on glossy surfaces | Bounce rays with roughness < 0.25 kept seeing the visible sun disk (×40) *and* the sun was added by next-event estimation | Sun as a proper area light: next-event estimation and bounce rays combined with **multiple importance sampling** (power heuristic) |
| 1.7 | Windows cast no shadow / no tint | Shadow rays skipped glass and water entirely | Shadow rays accumulate transmittance: tint × (1 − Fresnel) per crossing |
| 1.8 | Rough metals/stone too dark | Single-scattering GGX loses energy | Multi-scatter energy compensation (Karis fit, Fdez-Agüera form) in evaluation and sampling |
| 1.9 | Sky lighting inconsistent | Bounce-ray sky = 0.8 × the sky the camera sees | One sky radiance for both |

BVH stack-depth evidence: the v0.10 builder reached depth 18–28 on adversarial
inputs written for this audit (exponential spacing, clusters from mm to km,
stacked duplicates, huge triangle + detail) — so 1.1 was latent, not observed,
but nothing guaranteed it.

**Tests:** `bvh::depth_tests` (adversarial inputs, structure/bounds validity,
forced median splits vs brute force); `tests/pathtrace_bvh.rs` renders with
deterministic centre rays and compares **every pixel's first-hit distance on
the GPU against a CPU brute-force intersection** — dense clutter (60 k
triangles) and a mixed-scale scene placed at survey coordinates (4200, −3100):
**0 mismatches of 6144 pixels** each. Mutation check: re-introducing the
drop-children-when-full behaviour makes the test fail (63 and 397 bad pixels).

## Phase 2 — Texture resolution and material quality

Verified in v0.10 `pathtrace.rs`: every map was resampled to **one global
size** chosen by layer count — ≤24 → 1024², ≤80 → 512², >80 → 256². Also
verified: both the viewport and path-tracer mip chains averaged **sRGB-encoded
bytes** (gamma-incorrect: mips darken and fine patterns lose contrast with
distance), and normal-map mips weren't renormalised.

New texture system (`pathtrace.rs`, `mips.rs`):
- **Per-resolution classes**: 512 / 1K / 2K / 4K, separate colour (sRGB) and
  data (linear: normal, roughness) `texture_2d_array`s → 8 sampled textures,
  within the core limit of 16 — no binding arrays / non-uniform indexing
  features needed, so it works on any wgpu adapter. Each map goes to the
  smallest class covering its native size (never downscaled by default).
- **VRAM budget** (default 3 GB, `LUMENCRAFT_PT_TEXTURE_MB`): only when
  exceeded, the largest maps are demoted one class at a time; smaller maps are
  never touched. Per-class layer limits respected (overflow moves down).
- **Correct mips** for both renderers: colour averaged in linear light,
  normals averaged as vectors and renormalised, data maps averaged directly.
- Correct colour spaces kept: sRGB for colour, linear for data.
- Fixed a **memory spike**: `queue.write_texture` keeps a staging copy until
  the next submission; neither the path tracer nor the viewport submitted
  while loading, so a model's whole texture set sat in RAM twice. Both now
  flush every ~256 MB. (The large-model benchmark went from being OOM-killed
  in the 6 GB VM to running.)

Results (large-model benchmark, 150 materials): v0.10 stored 144 colour maps
at **256 px** (48.7 MB). v0.11 keeps them native: **121 × 1K, 20 × 2K,
3 × 4K** (1 339 MB), no demotions.

**Tests:** `mips` unit tests (sRGB average of a black/white checker is 188,
not 127; normals stay unit length; sizes); budget/class planning tests;
`tests/pathtrace_textures.rs`: a 2048-px per-texel-noise map viewed at ~2 px
per texel among 120 other textured materials — path-traced vs rasterized
(full-res) correlation **0.99**; forcing demotion (budget 1 MB) drops it to
0.52 and the test fails, as it should.

## Phase 3 — GPU/CPU synchronisation

v0.10: `device.poll(Maintain::Wait)` after **every sample pass** (CPU idle
while the GPU works, GPU idle while the CPU prepares the next pass), full
readback of 48 bytes/pixel of f32 buffers for every preview update, CPU-side
averaging loops, new buffers per job.

v0.11:
- **Asynchronous passes**: up to two passes queued (tracked by submission
  index + `on_submitted_work_done` flags); `step()` returns within its time
  budget, waiting only on the oldest pass when it's expected to finish in
  time. Work continues on the GPU while the UI runs.
- **GPU timestamps** (`TIMESTAMP_QUERY`, requested only if the adapter has
  it) give exact pass times for batch sizing; completion timing otherwise.
- **Batching** sized to a per-use target (live preview 20 ms, photo/movie
  jobs 80 ms, headless 250 ms) with a 120 ms per-dispatch cap (well inside
  the Windows 2 s TDR, even on an eGPU driving displays).
- **Adaptive queue depth**: if a submit is observed to block on queued work
  (seen with lavapipe; possible on some eGPU setups), that device drops to one
  pass in flight so the UI never waits a whole pass.
- **GPU resolve kernel** (`pt_resolve.wgsl`): averages and packs colour,
  albedo(+depth) and normal to fp16 with 256-byte rows: **24 bytes/pixel read
  back instead of 48**; the denoised fp16 plane is uploaded unchanged as the
  HDR image (no CPU conversion).
- Buffers pooled across jobs (the live preview restarts on every camera stop).
- Synchronisation kept where required: a job is drained before read-back;
  mapping waits on its own submission.

## Phase 4 — Denoising

Verified in v0.10: colour/albedo/normal correctly passed as FLOAT3 HDR, but the
filter was **re-created and committed on every call** (re-loading the network
weights for every preview update) and fed f32 copies built on the CPU.

v0.11: committed filters and their buffers are cached per image size; inputs
are the GPU-packed fp16 planes (`HALF3`, 8-byte pixel stride, padded rows);
**balanced** quality for intermediate preview updates, **high** for finished
images; when depth of field makes the guides noisy, final renders
**prefilter** albedo and normal first (`cleanAux`), as OIDN recommends for
detail preservation. OIDN picks CUDA on NVIDIA automatically. Wavelet
fallback runs on the same fp16 path (tested against the f32 path).
*Not done:* zero-copy GPU denoising — wgpu 22 has no CUDA interop, so data
still passes through host memory (now half as much).

## Phase 5 — FBX and import stability

Verified defects in the v0.10 binary FBX parser (each now a test):

| Defect | v0.10 result | v0.11 |
|---|---|---|
| Offset/length checks used unchecked `o + n` | wrap-around ⇒ out-of-bounds panic | `checked_add` |
| Node end offset could point backwards | infinite loop | must move forward; no-progress guard |
| Unbounded node nesting (binary and ASCII) | **stack overflow abort** (verified) | limit 128 |
| Array `count` from file used for `with_capacity` and zlib inflate unbounded | **OOM kill** on random corruption (verified) | ≤512 M elements, ≤8 GB per file, inflate stops at the declared size |
| Unknown array encodings treated as raw | garbage data | rejected |
| Property count larger than the node | long loops | rejected |
| `k * 3` / `k * 2` on file indices | overflow | checked |

Plus: `import::load` turns any remaining importer panic into an error message;
**exact duplicate meshes** (same material, vertices, triangles) are removed
from FBX imports. Existing FBX/OBJ/glTF tests all pass.
**Tests** (`tests/fbx_malformed.rs`, each under a watchdog): truncation at 300
points of 4 real files, 1 200 randomly corrupted files, crafted backwards
offsets / 4-billion-element arrays / a 64 MB zlib bomb / bad encodings /
huge property counts / 1 000- and 200 000-level nesting, and the importer
reporting a truncated file as an error.

## Phase 6 — Photorealism

Already present in v0.10 (kept): unidirectional path tracing, sun + local-light
next-event estimation, GGX VNDF + Lambert, Russian roulette (from bounce 3),
firefly clamp, thin glass, refractive water, foliage translucency, thin-lens
DOF. Added/fixed (beyond 1.6–1.9 above):

- **Glass no longer uses up the bounce budget.** Each glass/water crossing
  consumed a bounce, so light reaching a room through a double-sided pane at
  the last bounces was lost. Now only surface scattering counts (with a
  separate cap on total events).
- **Full light-sample weight at the final bounce** (MIS against a bounce that
  won't be traced lost its share — the sun on glossy surfaces at the last
  bounce was under-weighted).
- **Deeper presets**: Fast 4, High 8, Ultra 10, Max 14 bounces (live preview
  8). A white room loses ~18 % of its light at 5 bounces vs 14
  (`tests/pathtrace_portals.rs`); Russian roulette keeps the cost down.
- **Window (portal) sampling — implemented, tested, off by default.** Glass
  triangles act as an area-sampled guide to the sky, combined with bounce rays
  by MIS (pdfs summed over every pane crossed). Verified unbiased (mean
  radiance with/without within 1.1 % at 512 spp) and 43 % less variance per
  sample in the test room — but each sample costs ~2.3× (one extra long
  shadow ray), so variance × time is 1.29× *worse* there and 16 % *better* in
  the benchmark interior. Scene-dependent ⇒ opt-in:
  `LUMENCRAFT_WINDOW_SAMPLING=1`.

Image noise (16 spp vs each version's own 1024-spp reference, denoiser off,
160 × 90; hardware-independent):

| Scene | v0.10 RMSE | v0.11 RMSE | v0.11 + windows | Linear brightness v0.10 → v0.11 |
|---|---|---|---|---|
| Interior | 41.9 % | 44.8 % | 29.6 % | 0.1165 → 0.1197 (+2.7 %) |
| Small exterior | 9.0 % | 9.1 % | 9.0 % | 0.2496 → 0.2595 (+4.0 %) |

The interior is slightly noisier per sample in v0.11 because paths that used
to be cut off at windows now carry light (that light was simply missing).

## Phase 7 — GPU and memory

- Geometry/BVH, texture arrays and material table are cached separately
  (geometry keyed by mesh revisions + material assignment/type; textures by
  content keys + budget; materials by bytes). A no-change re-sync costs
  0.03–0.3 ms.
- Path-tracer memory is reported (`PathTracer::memory()`, logged per sync).
- No optional features are required; timestamps are used if present.
  Storage-buffer use stays at 8 per stage (portal table lives in the node
  buffer). GPU selection (Settings › Graphics card, `LUMENCRAFT_GPU`) unchanged.

**Interactive edit cost** — path-tracer re-sync until the live preview can
restart:

| Scene | Material edit v0.10 → v0.11 | Move one mesh v0.10 → v0.11 |
|---|---|---|
| Large model | 1 265 ms → **0.1 ms** | 1 154 ms → **203 ms** |
| Large exterior | 603 ms → **0.1 ms** | 550 ms → **384 ms** |
| Interior | 334 ms → **0.0 ms** | 342 ms → **211 ms** |

**End-to-end render time** at equal samples (320 × 180, 16 spp, 6 bounces,
OIDN, medians of 3 alternating runs, including the setup raster frame):

| Scene | v0.10 | v0.11 | Change |
|---|---|---|---|
| Small exterior (279 k tris) | 3.98 s | 3.97 s | −0.3 % |
| Large exterior (556 k tris, 400 plants) | 6.94 s | 7.70 s | +11 % |
| Interior (284 k tris) | 5.06 s | 5.85 s | +16 % |
| Large model (320 k tris, 150 materials) | 5.29 s | 4.86 s | −8 % (with 27× the texture data) |

The v0.11 per-sample kernel does more work (sun MIS pdfs, energy
compensation, glass transmittance in shadow rays, paths continuing through
glass); experiments ruled out the traversal stack size and material loads as
causes. On llvmpipe the asynchronous scheduling and smaller read-backs can't
show their benefit (its submissions are effectively synchronous and memory is
host memory); on a discrete GPU — especially over Thunderbolt — those are
exactly the costs v0.10 paid, but **this was not measurable here**.

Reproduce: `lumencraft --bench-pt all --size 1280x720 --spp 64 --out DIR`
(`LC_BENCH_NODENOISE=1`, `LC_BENCH_WINDOWS=1` for the noise/portal variants).

## Phase 8 — Validation

- `cargo fmt --check`: clean (added `rustfmt.toml` matching the house style;
  formatting applied in a separate commit).
- `cargo clippy --release --all-targets` (Linux) and `--target
  x86_64-pc-windows-gnu`: **no warnings or errors** (one documented allow:
  `6.28` in plant generation, kept so existing projects' trees don't change).
- `cargo test --release`: **57 tests, all passing** (23 new) — unit tests;
  `fbx`, `fbx_malformed`, `gpu`, `incremental`, `livesync`, `mapping`,
  `models`, `pathtrace_bvh`, `pathtrace_portals`, `pathtrace_textures`,
  `shaders` (offline naga validation of all 8 WGSL files), `texlib`,
  `textures`.
- Release builds: Linux and Windows (`x86_64-pc-windows-gnu`).

## API / format changes

- Project files: **unchanged** (no new fields; v0.10 projects load as before).
- `pathtrace` API: `resolve`, `compose`, `finish` take `&mut PtJob` (they
  drain in-flight work); new `read_layers`, `recycle`, `memory`, `bvh_depth`,
  `set_texture_budget`, `PtJob::target_ms`, `PathTracer::window_sampling`,
  `wanted_features`; `PtOpts::preset` bounce counts raised.
- `Renderer::set_hdr_override_packed` (fp16 rows) added; `mips` module added.

## Remaining limitations

- No hardware ray tracing: wgpu 22 exposes no ray-query/acceleration-structure
  API, so RTX RT cores are unused; traversal is a compute-shader BVH.
- Viewport and path tracer each keep their own texture copies (~2× texture
  VRAM); sharing them needs bindless textures (optional features) — deferred.
- Texture arrays are square per class: non-square maps are stored square
  (2:1 maps use up to 2× memory).
- wgpu doesn't report free VRAM, so the texture budget is configured, not
  detected.
- Denoiser data round-trips through host memory (no wgpu↔CUDA interop).
- Emissive surfaces aren't light-sampled (small bright emitters are noisy);
  thin-glass model only (no thick-glass refraction/dispersion); no caustics.
- Window sampling is off by default (cost/benefit is scene-dependent).
- No RTX 5080/5090 or Thunderbolt measurements; per-sample kernel cost on
  llvmpipe is up to +16 % vs v0.10 in two of four scenes.
